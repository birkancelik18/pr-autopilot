---
description: Check gh, claude and jq, write the pr-autopilot config interactively, and install the 60-second poller (live by default)
---

Set up pr-autopilot for this user. Do these steps in order and stop with a clear message if one fails.

1. Check requirements by running: `gh auth status`, `jq --version`, `git --version`, `claude --version`. If `gh` is not logged in, tell the user to run `gh auth login` and stop. Note that `claude` must be logged in with the user's own account (run `claude auth status` if available).
2. Run `gh api user --jq .login` and tell the user that everything pr-autopilot posts will appear as that login.
3. Ask the user which repos to watch (`owner/name`) and the absolute path of their local clone of each (verify each path is a git checkout whose `origin` points at that repo; the clone must have an `origin` remote). Optionally ask for a Slack incoming-webhook URL, `max_parallel` (default 2), and `review_skills`: absolute paths to the user's own review skill files (a `SKILL.md` or any markdown), each run as an extra review pass next to the built-in bugs, security and conventions passes; check each path exists.
3b. On macOS ask how they want to hear about results (`notify_style`), and say plainly what each needs:
   - `window` (default): a small window per result with an **Open PR** button that opens the PR; it closes itself after a minute. Works right away, nothing to install or allow.
   - `notification`: a normal banner; a click opens the PR. It needs `terminal-notifier` (`brew install terminal-notifier`; offer to run it) AND macOS permission for it. Send a test now: `terminal-notifier -title pr-autopilot -message "Click to open the repo" -open https://github.com/<first repo>`. If it exits non-zero or nothing shows, tell them to open System Settings → Notifications → terminal-notifier and turn on Allow notifications, then retry the test. Until it is allowed they still get plain notifications, but a click opens Script Editor instead of the PR.
4. Write `~/.config/pr-autopilot/config.json` (create the directory) following `${CLAUDE_PLUGIN_ROOT}/config.example.json`. Set `"dry_run": false` (live by default). If a config already exists, show it and ask before overwriting.
5. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/install-scheduler.sh" install`. It copies the plugin to `~/.local/share/pr-autopilot/plugin` and installs a launchd job (macOS) or systemd user timer / cron entry (Linux) that runs the poller every 60 seconds.
6. Tell the user: it is LIVE, so from the next poll it posts reviews, pushes fixes and replies as their login; results appear as notifications (or windows), at the top of Claude's reply to their next message in any Claude Code chat, live with `/pr-autopilot:watch`, and in `/pr-autopilot:status`. To try it without posting first, they set `"dry_run": true` in the config (no restart needed); `/pr-autopilot:pause` stops everything at once. Say that it does not replay the backlog: only PRs updated after setup are acted on (use `/pr-autopilot:replay` for older ones). Remind them to re-run `/pr-autopilot:setup` after updating the plugin so the installed copy is refreshed. GitHub notifications do not need to be on: it finds review requests through GitHub search.
